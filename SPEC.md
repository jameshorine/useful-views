# useful-views: specification (minimum version)

Build a Python package called `useful-views` (import name `useful_views`,
CLI command `useful-views`).

This is the minimum framework. Section 12 lists what is deliberately left for
later; do not build any of it now.

`README.md` in this repository is written by the project owner and agrees
with this spec. Section 13 says how to treat it.

Items marked **ASSUMPTION** are defaults chosen while writing this spec, not
confirmed requirements. Implement them, but list them back in your plan so
they can be confirmed or struck.

## 1. Purpose

Help a researcher turn raw data files into documented derived tables called
"useful views". The package generates and maintains a fixed project structure,
so every project looks the same and every view records which recipe made it.

## 2. Users

- PhD students in years 1 to 4, in fields such as economics, often in
  notebooks, often with AI coding tools. Engineering experience varies widely.
- A senior lead who reviews their work in git.
- The group uses both Python and R. This version runs Python steps only, but
  nothing in the layout or file formats may assume Python.

Design for the least experienced student: the tool must accept the script
they would have written anyway, as long as it sits in a recipe folder and
starts with a sentence saying what it does.

## 3. Vocabulary

- **Raw input**: a file in `raw/`. Nothing in `raw/` is produced by a recipe.
- **Recipe**: a folder in `recipes/`. From the inputs it declares, it produces
  the useful views it declares, by running its step files in order. It is the
  unit you run and the unit a view points back to.
- **Step**: one file in a recipe folder. It performs at least one non-trivial
  transformation of the data. That is the minimum; there is no maximum, and
  the author decides where one step ends and the next begins. A recipe has at
  least one step.
- **Work**: intermediate files in `work/<recipe>/`, read only by later steps
  of the same recipe.
- **Useful view**: a declared output of a recipe, in `useful-views/`. Every
  view is produced by exactly one recipe. A view may be an input to another
  recipe. Anything read from outside the recipe that made it must be a view,
  not a work file.

The package cannot judge whether a transformation is non-trivial and must not
try. That part of the definition is guidance for authors.

## 4. Who writes what

| File | Author |
|---|---|
| `README.md` (project root) | Humans. `init` writes a starter only if none exists, then never touches it. |
| everything in `recipes/` | Humans, with or without AI tools. `new_recipe` writes a template once, then the package never touches it. |
| `datapackage.json` | The package. Never hand-edited. |
| `useful-views/README.md` | The package. Regenerated on every successful run. |
| `.gitignore` | The package, at `init`, only if none exists. |
| `raw/*`, `work/*`, views | Raw files are placed by humans. Work files and views are written by steps. |

No file has two authors.

## 5. Project structure the package must produce, every time

```
my-data-project/
├── README.md                     # written by humans; documents the data project
├── datapackage.json              # generated: resources and recipes (never hand-edited)
├── .gitignore                    # generated by init: ignores raw/ contents and work/
│
├── raw/                          # raw inputs: git-ignored, never written by a recipe
│   ├── .gitkeep                  # keeps the folder in git
│   └── pwt110_bra_deu_esp_usa.csv
│
├── recipes/                      # written by humans, with or without AI tools
│   ├── pwt_panel/                # one folder = one recipe
│   │   ├── recipe.toml           # description, inputs, outputs
│   │   ├── 01_reshape_long.py    # one file = one step; top comment is its description
│   │   ├── 02_keep_core_variables.py
│   │   └── 03_pivot_to_panel.py
│   │
│   └── gdp_per_capita/           # a second recipe, taking a view as its input
│       ├── recipe.toml           # inputs = ["useful-views/pwt-panel.parquet"]
│       └── 01_derive_measures.py # smallest valid recipe: one step file
│
├── work/                         # intermediates, never recorded, git-ignored
│   ├── pwt_panel/                # one scratch folder per recipe, emptied before each run
│   │   ├── long.parquet
│   │   └── core.parquet
│   └── gdp_per_capita/
│
└── useful-views/                 # declared outputs only, flat
    ├── README.md                 # generated: catalog of the views and how each was made
    ├── pwt-panel.parquet         # produced by recipes/pwt_panel
    └── gdp-per-capita.parquet    # produced by recipes/gdp_per_capita
```

The generated `.gitignore` is exactly:

```
raw/*
!raw/.gitkeep
work/
```

The starter project README explains the structure and the conventions in
section 6, so a new student or an AI tool can write a compliant recipe from it.

**ASSUMPTION**: `useful-views/` is committed to git, not ignored.

## 6. Writing a recipe

`reference/recipes/` holds two canonical examples.

`recipes/pwt_panel/recipe.toml`:

```toml
description = "Country-year panel of core Penn World Table variables for Brazil, Germany, Spain and the United States."
inputs  = ["raw/pwt110_bra_deu_esp_usa.csv"]
outputs = ["useful-views/pwt-panel.parquet"]
```

`recipes/pwt_panel/01_reshape_long.py`:

```python
# Reshape the wide export (one column per year) into one row per country, variable and year.
import polars as pl

wide = pl.read_csv("raw/pwt110_bra_deu_esp_usa.csv")
long = wide.unpivot(
    index=["ISO code", "Country", "Variable code", "Variable name"],
    variable_name="year",
    value_name="value",
).with_columns(pl.col("year").cast(pl.Int32))
long.write_parquet("work/pwt_panel/long.parquet")
```

Format:

- The folder name is the recipe name: lowercase letters, digits, underscores.
- `description`: required, non-empty.
- `inputs`: a list of at least one path. Each is a file under `raw/`
  (subfolders allowed) or a file directly inside `useful-views/`.
- `outputs`: a list of at least one path. Each is a file directly inside
  `useful-views/`, and not `useful-views/README.md`. **ASSUMPTION**: a recipe
  may declare more than one output.
- All paths are relative to the project root and use forward slashes. The
  path written in `recipe.toml` is the same string the step uses in its code,
  and the same string a downstream recipe uses to name the view as an input.
- Step files are named `NN_name.py`: two digits, an underscore, a name. They
  run in numeric order. The step's name is the part after the underscore.
  Any other file in the folder is ignored.
- A step's description is the unbroken block of lines starting with `#` at
  the very top of its file, joined with spaces. Required. (`#` begins a
  comment in both Python and R.)
- Steps are ordinary scripts. They run with the project root as the working
  directory, use plain relative paths, and do not import `useful_views`. The
  package has no opinion on which data library a step uses.
- Steps hand data to each other only through files in `work/<recipe>/`.
- A recipe never writes to `raw/` and never reads another recipe's work files.

Views are tables. **ASSUMPTION**: a view is a `.parquet` or `.csv` file;
parquet is what the template and examples use.

The template written by `new_recipe` uses the marker `TODO` at the start of
the recipe description and of the stub step's top comment.

## 7. datapackage.json

`reference/datapackage.json` is the target for the reference project. Match
its structure, keys and ordering exactly.

It is always rebuilt from the set of recorded recipes. A recipe becomes
recorded when it first runs successfully, and each later successful run
replaces its record wholesale.

- `name`: the project folder's name, lowercased, with anything other than
  letters, digits, `-`, `_` and `.` replaced by `-`.
- `resources`, in this order:
  1. every raw input used by a recorded recipe, sorted by path, with the
     schema Frictionless infers;
  2. for each recorded recipe in name order, its views sorted by path, each
     with its inferred schema and
     `"producedBy": {"recipe": "<name>", "inputs": [<paths>]}`.
- A resource's name is its file name without the extension.
- `recipes`: the recorded recipes sorted by name, each with name,
  description, path, inputs, outputs, and steps (name, path, description, in
  run order), copied from the recipe folder at run time.

`recipes` and `producedBy` are custom properties. Frictionless preserves and
ignores them. Do not record hashes, sizes or timestamps in this version.

## 8. useful-views/README.md

A catalog of the views, generated from `datapackage.json` alone and rewritten
whenever `datapackage.json` is. `reference/useful-views/README.md` is the
target; match it exactly. For each view it gives the recipe's description,
the recipe folder, the inputs, the numbered step descriptions, and the
columns with their types.

## 9. Interfaces

The Python API is the primary interface. The CLI is a thin wrapper over the
same functions and adds nothing of its own.

- Every operation is a function that returns a useful value and raises a clear
  exception on failure. No `sys.exit` inside the library.
- The CLI turns exceptions into readable messages and non-zero exit codes.
- Functions must work when called from a subfolder such as `notebooks/`: find
  the project root by walking up to `datapackage.json`, and accept an explicit
  `root` argument.

| Python | CLI | What it does |
|---|---|---|
| `init(path=".")` | `useful-views init [path]` | Create the structure in section 5. Safe to run twice; never overwrites a file. |
| `new_recipe(name)` | `useful-views new-recipe <name>` | Create `recipes/<name>/` with a template `recipe.toml` and one stub step, `01_first_step.py`. Refuse if the folder exists. |
| `run(recipe)` | `useful-views run <recipe>` | Run one recipe and record what it produced. |
| `check()` | `useful-views check` | Report the state of the project. |
| `root()` | none | Return the project root as a path, so a notebook can read a view with its own library. |

`check()` reports:

- a declared input that is missing from disk;
- a recipe folder that has never been run successfully;
- a recorded recipe whose folder no longer exists;
- a recorded view whose file is missing;
- a file in `useful-views/`, other than `README.md`, that no recipe declares.

It does not detect changes to file contents. The CLI exits non-zero if it
reports anything.

## 10. Rules

Before a run, and before anything is changed on disk, refuse with a clear
message if:

1. `recipe.toml` is missing or unreadable, lacks `description`, `inputs` or
   `outputs`, or its description starts with `TODO`.
2. The recipe has no step file; a step file has no top comment, or one that
   starts with `TODO`; or two step files share a number.
3. A file in the recipe folder is named like a step but is not `.py` (for
   example `02_clean.R`). Say that only Python steps are supported so far.
4. An input is not a file under `raw/` or directly inside `useful-views/`, or
   does not exist.
5. An input inside `useful-views/` is not declared as an output by any recipe.
6. The recipe would create a cycle, taking its own output as an input directly
   or through a chain of other recipes.
7. An output is not a file directly inside `useful-views/`, is
   `useful-views/README.md`, or is already declared by another recipe.
8. Recording the run would give two resources the same name (two recorded
   files with the same name before the extension). Name both files.

Rules 5 to 7 read every other recipe's `recipe.toml`. If one of those is
unreadable, warn, skip it, and continue.

During a run:

9. Delete this recipe's declared outputs and empty `work/<recipe>/`, so a
   leftover file can never pass for a fresh result.
10. Run each step file in order as its own process, using the same Python
    interpreter that is running the package, with the project root as the
    working directory.
11. Stop at the first failing step, show its error output, and leave
    `datapackage.json` and `useful-views/README.md` unchanged.

After a run:

12. Every declared output must exist. If one is missing, fail, name it, and
    leave `datapackage.json` and `useful-views/README.md` unchanged.
13. Rebuild `datapackage.json` (section 7) and `useful-views/README.md`
    (section 8). Write each atomically.

Always:

14. `run(recipe)` runs that recipe only. It never runs upstream recipes.
15. Running the same recipe twice must leave `datapackage.json` and
    `useful-views/README.md` byte-for-byte unchanged.
16. Running one recipe must never alter another recipe's record.
17. When every recorded file is present, `frictionless validate
    datapackage.json` must pass.
18. Error messages must say what the human needs to fix and in which file,
    since the reader may be a person or an AI tool acting for one.
19. The package has no opinion on how large a step is.

A consequence of rules 9 and 11 to know about: after a failed run the
recipe's old views are gone while `datapackage.json` still describes the last
successful run. `check()` reports those views as missing. This is intended.

## 11. Technical constraints

- Python 3.11+ (for the built-in TOML reader).
- Dependencies: `frictionless`, `pandas`, `pyarrow`. Frictionless cannot read
  a parquet file without both of the others. They are internal; the package
  never asks a step author to use pandas.
- `polars` is a test dependency only, because the reference steps use it.
- Standard `pyproject.toml`, `src/` layout, pytest.
- Must work on Windows, macOS and Linux.
- Do not publish to PyPI. Do not upload anything.

## 12. Later, not now

Design so these can be added without changing the project layout, but do not
build them:

- Hashing of raw inputs, recipes and views, and everything that depends on it:
  detecting changed files, reporting a view as stale, refusing to run on a
  changed input.
- R steps: a step file `NN_name.R` in the same folder, run by `Rscript`.
- An upper limit on, or any measurement of, the size of a step.
- Recording where a raw input came from and how to fetch it.
- Running upstream recipes automatically; caching; scheduling.
- A command to remove a recipe's record.
- Handling raw data too large to keep inside the project.
- Subfolders under `useful-views/`.
- Notebooks as steps.

## 14. Done means

- A test builds the reference project from an empty folder using only the
  public functions, the file in `reference/raw/` and the files in
  `reference/recipes/`. Each resulting view has the same values as its
  counterpart in `reference/useful-views/` (compare values, not bytes).
  `datapackage.json` and `useful-views/README.md` equal the reference files,
  apart from the package `name`.
- Tests cover every refusal in rules 1 to 8, and: a failing step leaves both
  generated files untouched; a missing output is reported by name; a leftover
  output from an earlier run does not satisfy rule 12; a second run changes
  nothing; running one recipe leaves the other's record intact; `init` run
  twice changes nothing and does not overwrite an existing README or
  `.gitignore`; each item `check` reports; the API works when called from a
  subfolder.
- CLI tests run the same scenarios through the command line.
- `docs/quickstart.md` exists and its commands work as written.

## 15. How to work

- Read this file, `README.md` and everything in `reference/` first.
- Propose a plan, including the ASSUMPTION items, and wait for approval before
  writing code.
- Where this spec is silent or ambiguous, ask rather than guess.
- Run the tests and `frictionless validate` on the reference project before
  reporting anything as done, and report failures plainly.

## 16. About the reference folder

`reference/raw/pwt110_bra_deu_esp_usa.csv` is an extract of the Penn World
Table 11.0, licensed CC BY 4.0; `reference/README.md` records its source and
the required citation, and must stay with the data. The raw file begins with
a byte-order mark, which Frictionless records as the encoding `utf-8-sig`.
The two recipe folders are the intended authoring format. `datapackage.json`, the two views and
`useful-views/README.md` were produced by a throwaway script that acted out
rules 9 to 13 on those recipes, to confirm the numbers, that a second run
changes nothing, and that the result validates. No package code exists yet.
