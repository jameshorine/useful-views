A useful-views project is a folder with a fixed layout. Every project looks
the same, so a co-author, a reviewer or an AI tool knows where everything is.

```text
my-project/
├── README.md              # yours: the project and its data
├── sources.toml           # yours, optional: where each raw file comes from
├── AGENTS.md              # instructions for AI coding assistants
├── datapackage.json       # generated: what each recipe made, from what
├── cookbook.json          # generated by useful-views cookbook: the recipes, in run order
├── .gitignore
│
├── raw/                   # raw inputs, placed by hand, in any format
│   └── .gitkeep           # keeps the folder in git
│
├── recipes/               # one folder per recipe, written by you, an AI tool, or both
│   ├── recipe_01/
│   │   ├── recipe.toml    # description, inputs, outputs, and the steps
│   │   ├── 01_first_step.py
│   │   └── 02_second_step.py
│   └── recipe_02/         # inputs = ["useful-views/recipe-01.parquet"]
│       ├── recipe.toml
│       └── 01_only_step.py  # one step is enough
│
├── work/                  # in-between files, in any format, one folder per recipe
│   └── recipe_01/
│
└── useful-views/          # the views, flat
    ├── README.md          # generated: the catalog of the views
    ├── recipe-01.parquet  # made by recipes/recipe_01
    └── recipe-02.parquet  # made by recipes/recipe_02
```

## Make a project

```sh
useful-views init my-project
```

Or start from a ready-made example with `useful-views example pwt`.

`init` refuses your home folder and the top of a drive, since every folder
below would be inside the project. Pass `--force` if you mean it. Projects
can't be nested.

Commands and functions find the project from any folder inside it. See
[From Python](../guides/python.qmd#work-in-a-notebook-in-the-project).

## What lives where

| Kind | Where | Made by | In git |
|---|---|---|---|
| Raw input | `raw/`, subfolders allowed | you, by hand | no |
| Work file | `work/<recipe>/` | a recipe's steps, for its own later steps | no |
| View | `useful-views/`, flat | a recipe, as a declared output | no |
| Record and catalog | `datapackage.json`, `useful-views/README.md` | useful-views, after each successful run | yes |
| Cookbook | `cookbook.json` | `useful-views cookbook`, from the record | yes |

- **Raw inputs** are the data you start from. No recipe writes to `raw/`.
  Say where each file came from in [`sources.toml`](sources.md) and in the
  project's `README.md`.
- **Work files** pass data from one step to the next within a recipe. No
  other recipe may read them, and nothing records them. `run` empties
  `work/<recipe>/` before each run, so a leftover never passes for a fresh
  result.
- **Views** are the derived tables you use. Each is a parquet file made by
  exactly one recipe. Another recipe may read it as an input.
- **Records** say which recipe made each view, from which inputs, with which
  steps. See [Records](records.md).

Views are parquet files because parquet keeps each column's type. The record
and the catalog can then say exactly what each view holds. Other view
formats are [planned](https://github.com/jameshorine/useful-views/issues/34).

[Get started](../quickstart.md) says who writes each file.

## What to commit

`init` writes this `.gitignore` if the folder has none:

```text
raw/*
!raw/.gitkeep
/work/
useful-views/*.parquet
__pycache__/
```

Run `git init` in the project folder, then commit everything git doesn't
ignore:

- `README.md`, `sources.toml` and `AGENTS.md`;
- `recipes/`;
- `datapackage.json`, `useful-views/README.md` and `cookbook.json`;
- `.gitignore` and `raw/.gitkeep`;
- the files that list your steps' libraries, such as `pyproject.toml` and
  `uv.lock` (see [Installation](../installation.md#record-the-environment)).

The raw data, `work/` and the views stay out of git. Before each commit, run
`useful-views sync`, then `useful-views cookbook`.

If the folder already has a `.gitignore`, `init` leaves it alone. It warns
if git wouldn't ignore the raw data, work files or views, and names the lines
to add.

## Clone a project

A co-author who clones the project:

1. installs the libraries, for example with `uv sync`;
2. places the raw files, as the project's `README.md` describes;
3. runs `useful-views sync`, which makes every view again, upstream first.

## Share raw data

`raw/` isn't in git, because raw data is often large, private or licensed.
Share it the way its license allows:

- the original source, with the exact download date;
- your institution's storage;
- a data repository.

Say which in [`sources.toml`](sources.md). `datapackage.json` lists every raw
file each recipe read, with its columns and its source, so a co-author can
check they have the right files.
